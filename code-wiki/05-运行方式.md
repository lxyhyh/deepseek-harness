# 05 - 运行方式

本文介绍 DeepSeek Harness 的安装、运行、构建、测试与发布方式。

## 1. 环境要求

- **Node.js**：`^22.19.0 || >=24.0.0`
- **包管理器**：`pnpm`（固定版本 `11.7.0`，见根 `package.json` 的 `packageManager` 字段）
- 仓库是 **pnpm workspace** 单仓库，工作区包含：`vendor/*`、`packages/*/*`、`native/landlock-run`、`apps/*`、`website`。

## 2. 从头运行（推荐给开发者）

```sh
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
pnpm install
pnpm run build
pnpm dsh web
```

- `pnpm dsh web` 启动 Web UI，默认服务在 `http://127.0.0.1:3080`。
- `web` 与 `headless` 两个 profile 首次使用时会从内置模板自动初始化；其它 profile 需通过 `dsh plugin` 创建。

### 从 npm 直接运行（不需要源码）

```sh
npx @deepseek-ai/dsh web
```

## 3. dsh CLI 命令

`dsh` 命令是 profile 的产品启动器（`apps/cli/src/bin.ts`）：

| 命令 | 用途 |
|---|---|
| `dsh --profile <name>` | 启动指定 profile（在 `$DSH_HOME/profiles/<name>` 下） |
| `dsh --profile headless "job"` | 运行一个一次性持久会话，打印最终答案后退出 |
| `dsh web` | `--profile web` 的别名 |
| `dsh plugin --profile <name> <pnpm args>` | 管理某 profile 的插件（转发给 pnpm） |

参数规则：启动器只解析自己的 flag，其余传给 profile 内的应用插件（如 `dsh --profile web --port 8080` 中 `--port` 属于 web 应用）。

用 `--dump-config` / `--dump-default-config` 可查看组合出的插件树而不启动。

## 4. 常用开发命令

在仓库根目录执行：

| 命令 | 作用 |
|---|---|
| `pnpm install` | 安装依赖 |
| `pnpm run clean` | 清理构建产物与已删除包的残留 |
| `pnpm run build` | 构建（lib + web） |
| `pnpm run dev:web` | 前端 web 开发模式（`tsx scripts/dev-web.ts --poll`） |
| `pnpm run test` | 单元测试（vitest） |
| `pnpm run test:coverage` | 覆盖率门禁（`packages/*/*/src` 每文件 100%） |
| `pnpm run test:e2e` | 真实 API 测试（无 `DEEPSEEK_API_KEY` 时自动跳过） |
| `pnpm run test:snapshot` | 无需 key 的 ACP/headless 重放快照测试 |
| `pnpm run test:web` | Web 前端测试（需先 build） |
| `pnpm run typecheck` | 类型检查 |
| `pnpm run lint` | Lint（oxlint） |
| `pnpm run duplication` | 跨文件克隆检测 |
| `pnpm run hygiene` | knip + publint + 工作区约束 + 包不变式等 |
| `pnpm run doc-sync` | 文档门禁 |
| `pnpm run website:build` | VitePress 文档网站构建 |
| `pnpm dsh --profile headless "task"` | 从源码运行一个任务（需 `DEEPSEEK_API_KEY`） |

### 演示命令（需 API key）

```sh
pnpm run demo:code-mode   # Code Mode 演示
pnpm run demo:cordis      # agent 修改自身运行时演示
pnpm run demo:acp         # ACP 自动化服务器演示
```

## 5. 项目运行全流程（一次交互如何发生）

1. `dsh web`（或 `headless`）启动，boot 层按 profile 组合插件树（bundles + patch 层）。
2. `agent-loop` 创建 agent 与 session，启动主循环。
3. 用户输入经 Web UI/harness 进入 agent 的 inbox。
4. 主循环：组装系统提示词 + 工具 schema → 调 `ctx.llm` 请求模型 → 模型返回 assistant 消息或工具调用。
5. 工具调用经 `ctx.tools` 流水线执行（策略/审批/超时/结果）。
6. 整个过程追加到 session 日志，持久化插件异步落盘。
7. 需要时模型可再调工具，直到回合结束。

## 6. 环境变量与密钥

- 真实 API 测试与演示读取根目录 `.env` 中的 `DEEPSEEK_API_KEY`（可选 `DEEPSEEK_BASE_URL`）。
- 没有 key 时，e2e 测试自动跳过，快照测试使用录制/重放。

## 7. 发布与 CI

- 发布相关脚本在 `scripts/release/`：`bump`、`pack`、`verify-packed-install`、`publish`。
- CI 在 `.github/workflows/ci.yml`，分多个门禁（static、coverage、snapshot、artifacts、consumers 等），由 `scripts/run-gates.ts` 调度。
- 依赖升级、Vendored 包更新有专门流程（见 `vendor/README.md`）。

## 8. 常见问题定位

- 想看到机器实际启动的插件树：`dsh --profile web --dump-config`。
- 想了解某个子系统：`docs/subsystems/` 下几乎每个子系统都有专门文档。
- 想扩展能力：参考 `docs/cookbook/extension-cookbook.md` 与 `docs/architecture.md#where-new-behavior-goes`。
